01 · The problem

A travelling salesman whose cities never stop moving

ESA's Advanced Concepts Team published the Keplerian travelling salesperson problem in 2026 with a set of benchmark instances [1]. A spacecraft starts at one body, has to rendezvous with every other one, and come home before the window closes. Each leg is a Lambert arc between two dates on a grid, and costs the velocity change at departure plus the one at arrival. The goal is the smallest total Δv.

WHY IT IS HARD

The distances change every day

The same pair of asteroids can cost 2 km/s one month and 20 km/s the next. The order and the dates are one problem, not two.

FIRST, TRUST

Same problem, to the cent

I wrote my own cost tables and an exact solver. It reproduces all __NEXACT__ optimal values ACT published for up to 10 bodies, each in about a second.

THEN, SEARCH

20 to 80 bodies

Thirteen harder instances, several still open: the best tour found by a commercial solver sits far above the proven lower bound.

03 · The idea

Keep the clock open

Don't decide the dates until the tour is finished

A classic beam search builds tours body by body and keeps the best few thousand partial tours. To compare them it fixes when the spacecraft arrives at each body. On a fine time grid that locks in early dates that later turn out expensive, and there is no way back.

Mine keeps a whole curve for every partial tour: the cheapest Δv to be at the current body, ready to leave, for every date on the grid. Adding a leg updates the curve exactly. Partial tours are ranked "on schedule": by the cost of the curve at the date where the tour would be if it spread its legs evenly.

For a finished order the same curves give the optimal dates exactly, so the local search that polishes tours (moving bodies, swapping, reversing short stretches) always compares perfectly timed tours.

Finer grids should help. With open timing they do

What this does and does not show

The new values are upper bounds found by heuristic search; I cannot prove any of them optimal. On the small instances where the optimum is known my methods reach it, which says the search is sound, not that it is complete. The comparison is fair on the problem (same grid, same cost model, same rules) but not on computers: the old records came from a mixed-integer solver run for up to four hours on a large server, mine from heuristics on two CPU cores.

05 · The internship question

Can the search rule be discovered automatically?

ACT's topic asks to replace hand-designed parts of search methods with parts found by an automatic generate, test and refine loop [5, 6]. I tried it on the part that mattered most in my beam search: the rule that ranks partial tours. A genetic programming loop wrote rules as formulas over eight features of a partial tour, trained on six small instances, and each rule was then tested unchanged on eight instances it had never seen.

  • It rediscovered the principle.Starting from random formulas, every run arrived at the same idea as my hand rule: judge a partial tour by its cost on schedule and penalise using up time. Ranking by cost alone is __COSTX__ times worse on the unseen instances.
  • It did not beat the hand rule.At beam width 200 the evolved rules range from __EVLO__% to __EVHI__% against it on unseen instances. The gains seen in training did not transfer; the run seeded with my rule overfitted (__SEEDED__%).
  • The big gain was structural.Keeping the timing open changes how the search represents a tour. A search over formulas cannot invent that. A search over code, which is what language-model methods do [5, 6], could. That is the part I would most like to explore with the team.
06 · Limits, code, sources

What to keep in mind

  • The model is ACT's benchmark model: two-body dynamics, impulsive Lambert legs, dates on a fixed grid. Real low-thrust tours are a different problem.
  • All values are for the grid of each instance. A finer grid gives cheaper tours; comparisons are only made on the same grid.
  • My tours visit each body exactly once. ACT's formulation allows repeat visits, so a still cheaper tour could exist outside my search space.
  • The automatic discovery used genetic programming over a fixed set of features, not a language model: I had two CPU cores and no way to run one. The loop is the same generate, evaluate, select loop, so a model-based generator can replace the GP step.
  • Run times were short (minutes to about an hour per instance). Longer runs would probably improve the large instances further.

All code is public in the code folder: cost tables, exact solver, beam search, ant colony, MCTS, local search, the genetic programming loop and the independent checker. The instance files are ACT's own (Zenodo, doi:10.5281/zenodo.14850862). The new tours are in the JSON files linked in the table above; the 3D view reads viz.json.
