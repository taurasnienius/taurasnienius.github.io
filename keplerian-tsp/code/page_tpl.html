01 · The problem

A travelling salesman whose cities never stop moving

A spacecraft has to rendezvous with every asteroid in a group and come home before a deadline. ESA's Advanced Concepts Team published it as a benchmark in 2026 [1]. Every leg costs fuel (Δv), and the goal is the tour that costs the least.

03 · The idea

Keep the clock open

A classic beam search fixes the arrival dates early and cannot undo them. Mine decides the dates only when the tour is finished.

How it works

For every partial tour I keep a whole curve: the cheapest fuel cost to be at the current asteroid, ready to leave, for every date on the grid. Adding a leg updates the curve exactly.

Partial tours are ranked "on schedule": by their cost at the date they would reach if the legs were spread evenly.

Once the order is fixed, the same curves give the best dates exactly, so every tour the search compares is perfectly timed.

Carrying a cost curve over time along a route is a known technique in time-dependent routing [7]. What I did is apply it to this benchmark and its search methods.

Finer grids should help. With open timing they do

What this does and does not show

The new tours are the best found so far, not proven optimal. Same problem, same grid and same rules as ACT, but different computers: their records came from an exact solver running up to four hours on a large server, mine from heuristics on two CPU cores.

05 · The internship question

Can the search rule be discovered automatically?

ACT's topic: replace hand-designed parts of a search with parts found by a machine [5, 6]. I tried it on the rule that ranks partial tours. An evolution loop wrote formulas, trained on six small instances and was tested on eight unseen ones.

  • It rediscovered the principle.From random formulas, every run arrived at my hand rule's idea: judge a partial tour by its cost on schedule. Ranking by cost alone is __COSTX__ times worse.
  • It did not beat the hand rule.On unseen instances the evolved rules land between __EVLO__% and __EVHI__% of it. The training gains did not transfer, and the run seeded with my rule overfitted (__SEEDED__%).
  • The big gain was structural.Keeping the timing open changes how a tour is represented. A search over formulas cannot invent that. A search over code, which language models do [5, 6], could. That is what I would most like to explore with the team.
06 · Limits, code, sources

What to keep in mind

Five limits of this work, stated plainly.

  • A benchmark modelTwo-body dynamics, impulsive legs, dates on a fixed grid. Real low-thrust tours are a different problem.
  • One visit per bodyACT's rules allow repeat visits, so a cheaper tour could exist outside my search space.
  • Not proven optimalRuns were short, minutes to about an hour. Longer runs would probably improve the large instances further.
  • Same grid onlyA finer grid gives cheaper tours, so every comparison is made on the grid of its instance.
  • Evolution, not a language modelI had two CPU cores and no way to run one. The loop is the same generate, test, select loop, so a model can replace the formula generator.

All code is public in the code folder: cost tables, exact solver, beam search, ant colony, MCTS, local search, the evolution loop and the independent checker.
